> 适用方向：C++ 桌面客户端、Qt、图形/CAD、系统与性能、初中级社招及项目深挖。

## 使用原则

1. “完美回答”不是背全文，而是按“结论 → 原理 → 取舍 → 验证 → 局限”组织。
2. 以下第一人称表述只应保留自己真实完成的部分。若某模块由团队协作完成，要明确个人边界。
3. 数字只使用仓库可验证结果：四种构建配置各 32/32 测试通过；5000 文件正确性

4. 面试时优先讲 2–3 个最强证据，不要试图一次讲完所有功能。

## 一、项目介绍与价值（1–10）

### 1. 请用两分钟介绍 smartGraphics

**参考回答：**

smartGraphics 是一个面向 Windows 的二维 CAD/CAM 学习与技术展示项目，技术栈是
C++17、Qt 5.12.10、OpenGL、CMake 和 Ninja。它不是只画几条线的 Demo，而是把实体模型、
交互视口、图层与标注、撤销重做、原生持久化、DXF/DWG/SVG/位图导入、刀路排序和仿真串成
了完整工作流。

架构上我把几何、文档、IO、渲染、GUI 和应用入口拆成独立 CMake 目标；所有文档修改统一
通过 `SDocumentTransaction` 提交。项目中最有区分度的部分是像素精确位图矢量化：以四邻域
为语义基线，用水平同色游程、相邻行连接、并查集和有向边闭环替代逐像素 flood fill。正式
Release 基准固定种子测试 5000 张图片，三种实现结果完全一致；其中 4010 张为
4096×4096 压力图，多线程方案在该分布下累计取得 11.90× 相对基线加速。工程上还提供
32/64 位 Debug/Release 四套一键构建、Qt 自动发现、CTest、运行库部署和 GitHub Actions。

**证据：** [README](../README.md)、
[架构说明](ARCHITECTURE.md)、[测试结果](TEST_RESULTS.md)。

### 2. 这个项目解决了什么问题，目标用户是谁？

**参考回答：**

它解决两个层面的问题。产品层面，它提供一个可操作的二维 CAD/CAM 工作台，让用户能完成
绘制、编辑、图层管理、精确捕捉、文件交换以及简单刀路处理。技术层面，它验证了怎样用现代
C++ 和 Qt 把“几何算法—文档状态—交互预览—持久化—测试”做成闭环，而不是把算法散落在
按钮回调里。

目标用户首先是学习 CAD/CAM、Qt 图形客户端和 C++ 工程化的开发者；当前版本也可用于技术
演示和受控测试，但我不会把它描述为 AutoCAD 的生产级替代品，因为块、完整布局、代理对象
保留、插件 SDK 和三维能力仍不完整或不在范围内。

**证据：** [使用说明](USER_GUIDE.md)、
[功能差距矩阵](s_autocad_gap_matrix.yaml)。

### 3. 项目的核心功能有哪些？

**参考回答：**

我会按用户工作流而不是按类名罗列：第一，直线、圆弧、多段线、椭圆、样条、文字、标注和
填充等实体创建；第二，移动、旋转、缩放、镜像、修剪、延伸、打断、连接、圆角、倒角、阵列
和夹点编辑；第三，图层、线宽、线型、透明度、文字样式和标注样式；第四，原生 `.smartcad`
保存以及 DXF、DWG、SVG、位图交换；第五，对象捕捉、坐标输入、动态预览和撤销重做；第六，
刀路排序与仿真。

回答时我会强调“闭环”：一个功能只有同时进入实体模型、视口交互、事务、持久化或兼容性
处理以及自动测试，才算真正完成。

**证据：** [实施状态](s_implementation_status.md)、
[`SCadViewport`](../sgraphRender/s_cad_viewport.h)。

### 4. 你个人在项目中的职责是什么？

**参考回答：**

这题必须按真实经历回答，不能把仓库总代码量都算成个人贡献。一个合格的表述是：“我负责
的可验证边界是位图矢量化方案、批量正确性/性能基准，以及项目构建发布整理；同时对文档
事务、SVG 解析和对象捕捉中的具体问题做过修复。我的证据包括对应源码、5000 文件报告、
四套构建脚本和 32 项测试结果。GUI 中其他已有 CAD 功能我可以解释接口和集成方式，但不会
把未亲自实现的部分说成个人产出。”

如果确实由你独立完成更多模块，再逐项扩展；最好为每个声明准备一个提交、一个失败案例和
一个测试证据。

**证据：** [`sgraphIo`](../sgraphIo)、
[`sgraphVectorBenchmark`](../sgraphVectorBenchmark)、
[`sgraphBuildTools`](../sgraphBuildTools)。

### 5. 项目中最难的技术问题是什么？

**参考回答：**

最难的是在不改变“精确颜色 + 四邻域连通”语义的前提下，让位图色块提取既可并行又可验证。
难点不只是扫描快，而是要正确处理一对多、多对一、孔洞、狭窄通道、斜对角接触和棋盘格，
并保证单线程、多线程和 flood fill 得到同一组规范化轮廓。

我的方案把每行压缩为半开区间游程，相邻行同色区间只要有正长度重叠就连接，再用并查集合并
组件；边界使用整数格点有向线段表达，随后压缩共线段并闭环。最后不是靠肉眼验 SVG，而是
回栅格逐像素比较、比对轮廓 SHA-256、重新解析 SVG，并分别用 1000 个相对均衡案例和
5000 个偏重大图的压力案例验证。

**证据：** [`s_bitmap_run_vectorizer.cpp`](../sgraphIo/s_bitmap_run_vectorizer.cpp)、
[`s_bitmap_benchmark_validation.cpp`](../sgraphVectorBenchmark/src/s_bitmap_benchmark_validation.cpp)。

### 6. 你做过哪些关键技术取舍？

**参考回答：**

有三个关键取舍。第一，实体几何使用 `std::variant`，因为当前实体集合是封闭且数量可控的，
能获得值语义和集中持久化；代价是新增类型要修改多个访问点。第二，DWG 不直接链接 GPL
库，而是通过 LibreDWG 外部进程和临时 DXF 隔离，降低 ABI 和许可证耦合；代价是转换有降级
且当前同步等待会阻塞调用线程。第三，位图矢量化没有使用图像聚类或曲线拟合，而是保持像素
精确语义；代价是棋盘格等高边界复杂度输入仍会产生大量游程和轮廓。

取舍的判断标准依次是正确性、可解释性、可测试性，再是性能和功能覆盖。

### 7. 项目最有说服力的量化结果是什么？

**参考回答：**

我只讲可复现的数字。构建方面，Windows 下 32/64 位 Debug/Release 四套配置分别跑完
32/32 CTest，并完成 EXE 启动存活验证。算法方面，固定种子 `20260727` 的 5000 文件
Release 基准正确性 5000/5000；flood fill 累计 1,216,018.72 ms，游程单线程
279,075.69 ms，12 线程 102,223.19 ms，对应 11.90× 和 2.73×。逐文件加速比
P10/P50/P90 为 2.88×/13.70×/27.80×，峰值工作集 384.1 MB。

我同时说明口径：时间不包含 PNG 生成与报告生成，每种算法执行三次取中位数；5000 组中
4010 张是 4096×4096，因此它主要证明大图压力下的正确性和吞吐，不能泛化成任何机器、
任何图片都快 11.90×。较均衡的 1000 组总加速是 4.02×。

**证据：** [5000 文件 HTML 报告](../sgraphVectorBenchmark/results/5000-case-20260727/bitmap_vector_benchmark_report.html)。

### 8. 为什么说它不是“功能堆砌”？

**参考回答：**

判断依据是跨层闭环。比如一次编辑不是直接改视口缓存，而是由交互层生成几何结果，经
`SDocumentTransaction` 写入文档，形成撤销记录，发出文档信号触发刷新，再由原生格式或
DXF 路径持久化，并由 Qt Test 验证。位图导入也不是只有一个转换函数，而是设置、算法指标、
SVG 输出、重新解析、回栅格和失败附件的完整链路。

当然仍存在技术债，例如部分命令状态集中在较大的 `SCadViewport` 中、历史功能状态文档有
滞后、长耗时 IO 尚未全部异步化。我会主动讲这些边界，而不是用功能数量掩盖架构问题。

### 9. 为什么选择 C++17、Qt 5.12.10 和 Windows？

**参考回答：**

这是兼容性约束下的选择。C++17 提供 `std::variant`、`std::optional`、移动语义和成熟工具链，
足以支撑当前实体值模型；Qt 5.12.10 提供稳定的 Widgets、OpenGL、Concurrent、Test 和
Windows 部署工具；Windows 是当前 CAD 客户端、MSVC、现有 Qt 套件和 LibreDWG 发布包共同
决定的首要平台。

我不会说这是永远的最佳组合。Qt 5.12 已老，长期需要评估 Qt 6、C++20 和跨平台 CI。但升级
必须先处理第三方兼容、渲染差异、部署体积和文件行为回归，不能只改版本号。

### 10. 你如何定义这个项目“成功”？

**参考回答：**

我把成功拆成四个可观察标准：一是用户能完成从创建/导入到编辑、撤销、保存/导出的闭环；
二是核心算法在边界输入下可证明正确；三是仓库能由新环境按文档构建，而不是依赖作者机器；
四是已知缺口被诚实记录。

目前最强证据是四套构建、32 项测试、5000 文件基准、原子保存和兼容性报告。仍未达到的标准
包括生产级 DWG 无损往返、超大文档的空间索引与增量渲染、完善的后台任务取消，以及真实
用户长期使用数据。因此当前定位是 alpha 和技术展示，而不是商业 CAD 完成品。

## 二、架构设计（11–20）

### 11. 项目的整体架构是什么？

**参考回答：**

整体采用自底向上的分层目标：`sgraphCore` 提供通用结果类型；`sgraphGeometry` 定义实体和
纯几何；`sgraphDocument` 管状态、图层、历史和持久化；`sgraphCommands` 处理命令与坐标；
`sgraphIo` 负责交换格式和位图矢量化；`sgraphRender` 负责视口、选择和交互；`sgraphGui`
组织 Ribbon、停靠窗口和业务编排；`sgraphApp` 只负责启动。

价值不是目录好看，而是依赖方向可控：几何层不依赖主窗口，算法可直接测试；文档不需要知道
Ribbon；GUI 通过文档信号刷新。第三方组件单独放在 `sgraphThirdParty`，避免其类型扩散到
公共文档模型。

**证据：** [架构说明](ARCHITECTURE.md)、[根 CMake](../CMakeLists.txt)。

### 12. 如何控制模块之间的依赖？

**参考回答：**

主要用 CMake target 边界和接口类型控制，而不是全局包含路径。底层 target 通过
`target_link_libraries` 显式暴露依赖；IO 只面向 `SCadDocument` 和兼容性报告；视口只保存
文档观察指针；应用入口只链接 GUI。Clipper2 类型在 `s_polygon_boolean.cpp` 内转换，LibreDWG
只跨进程传 DXF 文件。

当前还不是绝对理想：`sgraphRender` 同时承担渲染、输入状态和大量 CAD 操作编排，后续应继续
把命令状态机和几何服务抽出，否则功能增长会让编译依赖和修改半径扩大。

### 13. 为什么实体模型选择 `std::variant` 而不是继承体系？

**参考回答：**

当前实体集合是封闭集合，并且文档历史、复制、序列化都需要稳定的值语义。`std::variant`
把几何数据直接放进 `SEntityRecord`，没有每个小实体的堆分配，也不会发生对象切片；复制一条
历史记录就是复制值，持久化时可按 `SEntityType` 明确分支。

代价是开放扩展较弱：新增实体必须同步修改绘制、范围、变换、捕捉、序列化和 IO 分支。
如果未来要公开第三方插件 SDK，我会在核心值模型外增加版本化的插件接口或类型擦除层，而
不是让插件直接扩展现有 variant。当前记录还同时保存 `SEntityType`，它与 variant 可能产生
重复事实不一致；审计会检查这一点，长期也可考虑从 variant 单一推导类型。

**证据：** [`s_entity.h`](../sgraphGeometry/s_entity.h)。

### 14. 文档、视口和主窗口如何分工？

**参考回答：**

`SCadDocument` 是权威状态源，保存实体、图层、样式、修改状态和历史；`SCadViewport` 是观察者
和交互控制器，负责坐标变换、选择、捕捉、预览与绘制；`SCadMainWindow` 负责把 Ribbon、
命令行、文件对话框、停靠面板和文档操作编排起来。

视口通过 `QPointer<SCadDocument>` 观察文档，连接 `documentChanged` 后调用 `update()`，不会
拥有文档。主窗口用 `std::unique_ptr` 拥有文档。这避免视口状态成为第二份事实源，也让纯文档
测试不必启动完整窗口。

### 15. 一次用户命令是怎样流经系统的？

**参考回答：**

以移动为例：Ribbon 或命令行把视口切到对应 `SToolMode`；视口采集选择集、基点和目标点，
移动过程中用纯几何函数生成预览副本；确认后开启文档事务，用同一几何结果替换实体并
`commit()`；文档写入 undo 栈、清空 redo 栈、设置 modified 并发信号；视口收到信号重绘，
属性面板和标题同步更新。

关键点是预览与提交尽量共用几何求解，避免“看见的”和“最终落图的”采用两套算法。

### 16. 为什么所有修改要经过 `SDocumentTransaction`？

**参考回答：**

它把跨多个实体的操作变成一个用户级原子动作。例如阵列、导入或多选移动可能同时新增、删除、
换层和调整顺序，如果每改一个实体就写历史，用户需要撤销很多次，失败时也容易留下半成品。

事务先在私有容器中暂存 added/removed entities、图层、绘图设置和实体顺序，显式提交时一次
交给文档形成 `SHistoryEntry`。它提供的是应用层原子边界，不是数据库隔离；这一点我会明确
区分。

**证据：** [`s_document_transaction.h`](../sgraphDocument/s_document_transaction.h)。

### 17. 文件编解码器接口是怎样设计的？

**参考回答：**

`SIFileCodec` 提供稳定的 `id/displayName/extensions/read/write` 虚接口，读写返回
`SResult<SFileCompatibilityReport>`。结果不仅表示成功失败，还记录导入、导出、跳过数量和
警告，让“成功但降级”不被误报为无损。

接口基类有虚析构，避免经基类指针销毁派生对象时产生未定义行为。当前接口适合进程内固定
编解码器，但尚不是 ABI 稳定插件接口；跨 DLL 还需 C ABI 工厂、版本协商、统一分配/释放和
异常边界。

**证据：** [`s_i_file_codec.h`](../sgraphIo/s_i_file_codec.h)。

### 18. 第三方库如何隔离？

**参考回答：**

我采用三种边界。SARibbon 和 QtADS 只服务 GUI target；Clipper2 在几何实现文件中做
`SPoint2d` 与第三方路径类型的双向转换，公共接口不暴露 Clipper2；LibreDWG 不链接进进程，
而是作为外部命令行工具，通过临时 R2000 DXF 交换。

这样做降低升级和许可证影响，但不是“用了外部进程就自动没有许可证义务”。仓库仍保留各
许可证和第三方声明，发布二进制前仍需满足 Qt、QtADS、Clipper2 和 LibreDWG 各自条款。

**证据：** [第三方声明](../THIRD_PARTY_NOTICES.md)、
[`s_polygon_boolean.cpp`](../sgraphGeometry/s_polygon_boolean.cpp)。

### 19. 为什么把源码拆成很多 `s_*.cpp`？

**参考回答：**

`SCadViewport` 和 `SCadMainWindow` 的公共类本身很大，如果所有实现都放在一个 CPP，任何小
改动都会扩大编译和评审范围。我按交互职责拆为 selection、tracking、curve trim、fillet、
array、render 等实现文件，共享同一个类声明和稳定公共接口。

这是一种过渡性的“按职责拆实现”，优点是低风险、无需改变外部 API；缺点是类的私有状态
仍然高度共享。规模继续增长时，应升级为独立命令对象/状态机和几何服务，而不只是继续增加
CPP 文件。

### 20. 当前架构最大的技术债是什么？

**参考回答：**

第一，视口类承担了渲染、选择、输入状态机和很多编辑编排，私有状态多，应该进一步分出命令
会话与选择服务。第二，实体查找多处仍在线性 `std::vector` 上进行，超大文档需要 ID 索引和
空间索引。第三，DWG 转换和某些大任务仍在调用线程同步等待。第四，历史状态按实体值复制，
大文档可能有较高内存放大。第五，功能状态文档存在历史版本号和现状不完全同步的问题。

我不会把这些描述为“以后再优化”就结束，而会按用户影响排序：先做后台任务与取消、实体/
空间索引、历史命令压缩，再处理插件和更大范围兼容性。

## 三、C++ 设计与资源安全（21–30）

### 21. 项目中的所有权是如何表达的？

**参考回答：**

主窗口对核心非 QWidget 服务使用 `std::unique_ptr`，例如文档、恢复管理器和仿真控制器；
Qt 创建的控件由 parent-child 树管理，成员只保留非拥有裸指针；视口用 `QPointer` 观察
`QObject` 文档，在对象销毁后自动变空。算法数据主要用值类型和 `std::vector`。

我会避免“裸指针一定危险”这种绝对说法。危险的是所有权不清：Qt 子对象裸指针是观察者，
`unique_ptr` 是唯一所有者，`QPointer` 是可失效观察者，这三种语义在接口上要能区分。当前
工作区控件仍有普通文档裸指针，虽受现有销毁顺序保护，重构时应改成 `QPointer` 或明确契约。

### 22. 为什么文档使用 `std::unique_ptr`，而很多控件用 Qt parent？

**参考回答：**

文档是主窗口明确拥有的非可视核心对象，用 `unique_ptr` 能在 C++ 类型层表达唯一所有权并
固定析构顺序。控件天然属于 QWidget 树，用 parent 可以随窗口统一销毁并支持 Qt 内部事件
机制。

恢复管理器同时有 `unique_ptr` 和 QObject parent，这在当前析构顺序下是安全的：成员先删除
对象，QObject 会从父对象 children 列表移除；但它有重复表达所有权的认知成本。若重构，我会
二选一：纯 `unique_ptr` 不设 parent，或 parent 拥有、成员保存 `QPointer`。

### 23. `QPointer<SCadDocument>` 解决了什么问题？

**参考回答：**

视口不拥有文档，但文档是 `QObject`，若只保存普通裸指针，在文档先销毁或切换时可能悬空。
`QPointer` 会在 QObject 析构时自动清零，所有绘制和交互入口先检查 `m_document`，因此能安全
失败。

它不是线程安全工具，也不能延长对象生命周期；如果跨线程访问文档，仍需遵守 QObject 线程
亲和性并通过 queued signal 或快照传递数据。

### 24. `SResult<T>` 为什么不用异常？

**参考回答：**

文件解析、外部工具、用户输入和算法校验失败都属于可预期错误，`SResult<T>` 让调用方在类型
和控制流上显式处理，并可把 `QString` 直接展示给 UI。它也避免异常跨 Qt 回调、第三方边界
或未来 DLL 边界。

但当前实现不是完整的 `expected`：失败对象仍默认构造一个 `T`，`value()` 也没有状态检查，
所以不适合不可默认构造类型，误用时不会自动阻止。更成熟的实现会用
`std::variant<T, Error>`、`std::optional<T>` 或 C++23 `std::expected`，并提供
`valueOr/transform` 等组合接口。

**证据：** [`s_result.h`](../sgraphCore/s_result.h)。

### 25. 项目在哪里体现了 RAII？

**参考回答：**

原生保存用 `QSaveFile`，对象离开作用域时自动清理未提交临时文件；DWG 转换用
`QTemporaryDir` 管临时目录；`QFile/QProcess/QElapsedTimer` 都由栈对象管理；文档和控制器
用 `unique_ptr`；容器持有实体值，不需要手动 `new/delete`。

RAII 的价值不是语法简洁，而是异常、早返回和多分支失败时资源仍能释放。例如 LibreDWG
转换任何一步失败，临时目录仍会自动删除；原子复制只有 `commit()` 成功才替换目标文件。

### 26. 项目如何使用移动语义？

**参考回答：**

事务把文本、顶点数组、几何 variant 和 added/removed 列表按值接收后 `std::move` 进入记录；
提交时把整批暂存实体移动给文档历史；位图轮廓、SVG 和测量结果也通过移动返回，避免大容器
深拷贝。

我不会说 `std::move` 本身会搬数据，它只是把表达式转换成可供移动重载选择的右值。真正收益
取决于 `QString/std::vector/QByteArray` 的移动实现；移动后的对象仍必须可析构和可赋值，
但其内容通常只保证“有效但未指定”。

### 27. 为什么 `SDocumentTransaction` 禁止拷贝？

**参考回答：**

事务代表一次唯一的提交意图。如果可拷贝，两份对象都可能持有同一批暂存修改和同一文档引用，
造成重复提交或难以定义的所有权。删除拷贝构造和拷贝赋值能在编译期阻止这种错误。

当前类也没有显式移动语义，通常由 `unique_ptr<SDocumentTransaction>` 持有，因此提交对象
身份稳定。若未来要直接按值返回事务，需要设计移动后状态，并确保只有一个对象能提交。

### 28. 返回 `const std::vector<SEntityRecord>&` 有什么生命周期风险？

**参考回答：**

它避免复制，但引用只在文档存活且容器未被修改到使引用/迭代器失效时有效。当前调用主要在
同一 UI 线程的短作用域中遍历，不跨事件循环保存元素引用，所以风险可控。

如果要支持后台渲染或异步分析，我不会把该引用直接交给线程，而会生成不可变快照、复制必要
字段，或引入读写锁和稳定存储。尤其 `std::vector` 插入重分配后，保存的元素指针会失效。

### 29. `SIFileCodec` 为什么必须有虚析构？

**参考回答：**

它是多态基类，编解码器很可能通过 `SIFileCodec*` 或智能指针持有。如果基类析构不是
`virtual`，经基类指针删除派生对象是未定义行为，派生资源不会被正确释放。当前接口显式写了
`virtual ~SIFileCodec() = default`。

不过“有虚析构”并不等于 ABI 稳定。跨动态库还要处理编译器、运行库、STL/Qt 类型、异常、
内存分配器和接口版本，当前项目尚未声称支持插件 ABI。

### 30. 如何排查 Debug 正常、Release 崩溃？

**参考回答：**

我会先把它当成未定义行为或竞态，而不是先怪优化器。步骤是：固定输入并最小化复现；比较
Debug/Release 编译选项和依赖架构；打开 `/W4`、静态分析及可用的 ASan/UBSan；检查悬空引用、
越界、未初始化、迭代器失效、数据竞争和错误的对象析构；再用带符号的 Release 栈和二分变更
定位。

本项目构建脚本还会解析 PE 头验证 EXE、Qt 和 QtADS 的 32/64 位一致性，减少“能链接但运行时
装错 DLL”这类伪 Release 问题。最终修复必须补自动测试，而不是降低优化级别绕过。

## 四、文档事务、撤销重做与持久化（31–40）

### 31. `SDocumentTransaction` 的工作流程是什么？

**参考回答：**

`beginTransaction(label)` 创建事务；调用方通过 `add/remove/replace/setEntityLayer` 等接口把
变化暂存在事务自己的容器中；确认后 `commit()` 将 added、removed、图层、绘图设置或实体
顺序一次性交给 `SCadDocument`。文档先应用变化，再构造 `SHistoryEntry`，推入 undo 栈、清空
redo 栈、设置 modified，并发出状态信号。

这样一次复杂命令只形成一个撤销单元。事务未提交时，暂存实体不会进入文档；但实体 ID 已经
预留，取消后可能出现 ID 空洞。ID 只要求稳定唯一而不要求连续，所以这是可接受取舍。

**证据：** [`s_document_transaction.cpp`](../sgraphDocument/s_document_transaction.cpp)。

### 32. 事务析构时为什么不自动提交或抛异常？

**参考回答：**

析构时自动提交会让“忘记调用 commit”从安全取消变成意外修改；析构抛异常又可能在栈展开时
触发 `std::terminate`。因此当前设计是显式提交，析构默认放弃暂存变更。

这也有可用性风险：开发者可能忘记提交而没有编译错误。改进方式可以是增加
`[[nodiscard]]` 的事务结果、状态断言或提供 `executeTransaction(label, lambda)`，由框架在
lambda 成功时统一提交、失败时取消。无论如何都不应在析构函数中隐式执行有业务副作用的
提交。

### 33. 撤销和重做是怎么实现的？

**参考回答：**

每个 `SHistoryEntry` 保存本次新增和删除的实体值，以及图层、绘图设置、样式和实体顺序的
before/after 快照。Undo 删除本次 added、恢复 removed，再应用 before 状态并把条目移到 redo
栈；Redo 做反向操作并移回 undo 栈。实体顺序通过 ID 到 rank 的映射后稳定排序恢复。

它比保存整个文档快照更节省普通编辑的内存，也容易把一次事务映射成一次撤销；但图层和样式
仍使用全量小表快照，大规模实体替换也会复制较多数据。

**证据：** [`s_cad_document_history.cpp`](../sgraphDocument/s_cad_document_history.cpp)。

### 34. 为什么新提交后要清空 redo 栈？

**参考回答：**

因为撤销后再执行新操作，文档已经进入一条新的历史分支，旧 redo 条目是基于另一状态构造的。
继续应用可能引用不存在的实体或破坏顺序。当前 `commitEntities` 在推入新的 undo 条目后明确
`m_redo_stack.clear()`，符合线性历史模型。

若要保留分支，需要显式设计历史 DAG、分支命名和状态快照；对桌面 CAD 的常规撤销语义而言，
这会显著增加复杂度，当前没有必要。

### 35. 文档的 modified 状态如何维护？

**参考回答：**

成功提交、undo、redo 和恢复副本后会设置 modified；普通保存成功后才把 modified 清零并
更新活动路径；`saveRecoveryCopy` 不改变活动路径和修改状态。窗口关闭前由 `maybeSave()`
根据 modified 决定是否提示。

当前 modified 是布尔值，并没有保存点对应的历史索引，所以“保存后 undo 再 redo 回保存点”
是否自动回到未修改状态还可以做得更精确。更完整的设计会记录 saved revision ID，并比较
当前历史节点。

### 36. 原生文件为什么使用 `QSaveFile`？

**参考回答：**

直接覆盖目标文件时，进程崩溃、磁盘满或写入失败可能破坏原文件。`QSaveFile` 先写同目录临时
文件，只有所有 `QDataStream` 写入成功且 `commit()` 成功后才原子替换目标；失败或对象析构会
清理临时文件。

项目在原生保存、恢复元数据、临时 R2000 DXF 和最终 DWG 复制中都采用该模式。它解决单文件
替换原子性，但不等于跨多个文件的事务，也不能替代备份和格式校验。

### 37. 原生 `.smartcad` 格式如何做版本兼容？

**参考回答：**

文件头有固定 magic `SMCAD001`，紧随 JSON manifest，其中包含 `formatVersion`、单位和精度等
元信息；二进制主体使用固定小端序和 `QDataStream::Qt_5_12`。当前源码版本是 24，读取时先
拒绝小于 1 或高于当前版本的文件，再按版本分支补默认字段或解析新字段。

这种显式迁移比直接序列化 C++ 对象布局稳定，不受 padding、vtable 和编译器 ABI 影响。
代价是每次新增字段都必须维护兼容分支和往返测试。

**证据：** [`s_cad_document_io.cpp`](../sgraphDocument/s_cad_document_io.cpp)。

### 38. 如何防御损坏或恶意构造的文件？

**参考回答：**

加载时先检查 magic、版本和 manifest 最大 1 MB；图层、实体等计数有上限；数值检查
`std::isfinite`、合法范围和枚举；读取结束检查 `QDataStream::status()`。重要的是先解析到
局部 `loaded_*` 容器，只有全部验证通过后才替换活动文档，避免半加载状态。

当前仍不是面向不可信网络输入的完整安全解析器：还应增加总文件大小/总分配预算、字符串长度
上限、模糊测试、递归/复杂度限制和安全审计。边界检查必须覆盖“不会越界”和“不会被超大合法
计数耗尽内存”两个维度。

### 39. 自动恢复和文档审计解决什么问题？

**参考回答：**

自动恢复负责进程异常前的数据可恢复性：定时写独立恢复副本和元数据，限制保留数量，恢复时
不把副本路径误当成用户原文件。审计负责逻辑一致性：检查无效几何、图层引用、线宽和多段线
数组等，`FIX` 模式把可修复变化作为一个可撤销事务提交。

两者边界不同：恢复应尽量保存现场，审计应在可解释规则下修复；不能在恢复时静默丢弃未知
数据。生产化还应加入崩溃标记、恢复副本校验和更明确的用户确认。

**证据：** [`s_document_recovery_manager.cpp`](../sgraphDocument/s_document_recovery_manager.cpp)、
[`s_cad_document_audit.cpp`](../sgraphDocument/s_cad_document_audit.cpp)。

### 40. 大文档下撤销重做会有什么性能问题，怎么优化？

**参考回答：**

当前实体存在 `std::vector`，删除会重复 `remove_if`，历史还复制完整实体；批量操作可能达到
O(N×M) 查找/删除并放大内存。实体顺序恢复虽用哈希 rank 降低查找，但仍需稳定排序。

优化顺序是先度量再改：用 `unordered_map<ID,index>` 或稳定句柄加速查找；批量删除构造 ID
集合后一次过滤；历史改为命令/delta、共享不可变几何或 copy-on-write；对连续拖动合并历史
条目；设置历史内存预算和检查点。优化必须继续保证事务原子性和撤销后字节/语义一致。

## 五、Qt、渲染与交互（41–50）

### 41. 应用启动时做了哪些关键配置？

**参考回答：**

在创建 `QApplication` 前开启高 DPI 缩放、高 DPI pixmap 和 OpenGL context 共享；设置默认
OpenGL 3.3 Core Profile 与 4× MSAA；随后初始化资源、组织名/应用名/版本、Qt 中文翻译和
自定义中文翻译，应用主题后创建并最大化主窗口。

必须在 QApplication 前设置的属性不能延后，否则部分平台不会生效。OpenGL 格式也应在任何
OpenGL widget 创建前设为默认。启动失败诊断要记录实际 context 版本和驱动回退，而不能只看
请求值。

**证据：** [`s_main.cpp`](../sgraphApp/s_main.cpp)。

### 42. 项目真的使用了 OpenGL 吗？

**参考回答：**

准确说，它使用 `QOpenGLWidget` 管理帧缓冲和 OpenGL context，在 `initializeGL` 初始化函数、
关闭深度测试，在 `paintGL` 用 `glClear` 清背景；实体、网格和覆盖层主要由 `QPainter` 绘制。
因此当前是“OpenGL 承载的 QPainter 2D 视口”，不是自己维护 VBO、shader 和批渲染管线。

优点是开发速度快、文字和 Qt 样式集成简单；缺点是超大实体量下 draw call 和 CPU 几何离散
会成为瓶颈。若性能数据证明需要升级，我会把静态几何缓存到 GPU，动态预览和文字仍用
QPainter/覆盖层，逐步迁移而非一次重写。

**证据：** [`s_cad_viewport_events.cpp`](../sgraphRender/s_cad_viewport_events.cpp)。

### 43. 世界坐标和屏幕坐标如何转换？

**参考回答：**

屏幕中心作为世界原点基准，X 轴按 `world.x * zoom` 正向映射，Y 轴因屏幕向下而取负，再叠加
pan offset。逆变换严格按相反顺序减中心和偏移、除以 zoom。缩放被限制在 0.01 到 10000，
避免除零和极端数值。

捕捉容差通常以屏幕像素定义，因此要除以 zoom 转成世界容差；否则同一几何在不同缩放级别下
手感不一致。长期还要考虑大坐标下 double 精度和浮动原点。

**证据：** [`s_cad_viewport_render.cpp`](../sgraphRender/s_cad_viewport_render.cpp)。

### 44. 如何避免 UI 卡死？

**参考回答：**

原则是 UI 对象只在 GUI 线程访问，耗时纯计算在工作线程执行，结果通过 queued signal 回主
线程提交；任务要支持取消、进度和对象失效检查。位图矢量化内部已经用线程池并行扫描和行间
连接，但调用方会等待 futures，因此“算法多线程”不等于“UI 一定不阻塞”。

`SCadDocument` 内部容器没有锁，它不是通用线程安全对象；后台任务只能处理不可变快照或值
输入，完成后回到 UI 线程提交事务。不能为了减少卡顿而从工作线程直接修改 QObject 文档。

当前 DWG `QProcess::waitForFinished` 最长 120 秒，也是明确技术债。生产化时我会把位图转换和
DWG 转换封装成后台 job，使用 `QFutureWatcher` 或 worker QObject，主线程只更新进度；完成时
再开一个短事务导入。取消后不提交半成品。

### 45. 动态预览如何保证和最终结果一致？

**参考回答：**

交互状态只记录用户输入、引用实体和参数，预览阶段调用独立几何函数生成临时
`SEntityRecord`，不修改文档；确认时用相同输入和同一几何函数得到结果，经事务替换或新增
实体。取消时清空预览状态即可。

测试要同时断言预览几何和提交后文档几何，而不是只测最终按钮。当前很多操作已共用
`translatedEntity`、offset、fillet、array 等几何路径，但视口状态仍较集中，进一步抽成命令
会话能更系统地保证一致。

### 46. 点选、窗口选择和交叉选择有什么区别？

**参考回答：**

点选根据光标世界坐标和与 zoom 相关的容差做命中；窗口选择要求实体边界完整位于矩形；交叉
选择只要实体与矩形相交或控制点进入就选中；Shift/修饰键用于追加。隐藏层不参与绘制，锁定
层不应进入可编辑选择集。

仅用包围盒会产生曲线假阳性，所以基础过滤后应根据实体类型做线段/圆弧/边界相交测试。实体
量增大后，需要 R-tree/quadtree 做候选召回，再精确判断。

### 47. 对象捕捉如何选择“最佳”候选？

**参考回答：**

算法先从各实体生成端点、中点、圆心、象限、最近点等候选，再计算线线、线圆、圆圆交点和
延伸/外观交点；候选必须在世界容差内。选择时结合类型优先级和距离，例如真实交点通常高于
最近点。端点与圆心受用户模式位控制，其他已实现类型按算法参与。

一个实际修复是过去的条件把“非端点且非圆心”的所有类型都错误过滤了；正确逻辑应只在候选
本身是 Endpoint/Center 时检查对应 mode bit。这个 bug 说明复杂布尔条件必须拆开并覆盖每类
候选测试。

**证据：** [`s_object_snap.cpp`](../sgraphRender/s_object_snap.cpp)、
[`s_precision_snap_test.cpp`](../sgraphTests/s_precision_snap_test.cpp)。

### 48. 为什么视口保存的是文档指针而不是复制实体？

**参考回答：**

文档是唯一事实源。视口如果复制实体，会出现同步、撤销和修改状态双写问题；每次文档变化后
还要维护两份版本。当前视口只在绘制时读取 `document.entities()`，预览另存临时副本，提交后
依赖 document signal 重绘。

对超大文档直接遍历可能慢，但解决方案应是文档快照、渲染缓存或空间索引，而不是让视口成为
第二个可修改文档。

### 49. 主题和高 DPI 是怎样处理的？

**参考回答：**

主题由 `SThemeManager` 读取深色、浅色和高对比度 token，图标通过主题感知 provider 生成；
UI scale 变化经 signal 触发主窗口更新尺寸。启动前开启 Qt 高 DPI 属性，资源图标使用高 DPI
pixmap。工作区和主题设置通过 `QSettings` 持久化。

验证不只看固定像素截图，而应测不同 scale 下最小尺寸、布局比例和控件可访问性。真实视觉
验收仍需要人工截图和不同 DPI 设备，因为 offscreen 单测不能发现所有平台字体和驱动差异。

### 50. Qt signal/slot 的生命周期安全吗？

**参考回答：**

当 sender 或 receiver 是 QObject 且被销毁时，Qt 会自动断开连接；切换文档时视口还会先
`disconnect(oldDocument, ..., this, ...)` 再连接新文档，避免旧状态继续触发。lambda 若捕获
`this`，连接时提供 receiver context，receiver 析构后连接失效。

需要避免的是无 context 的长期 lambda、捕获局部引用、跨线程直接调用 UI，以及在析构期间
触发依赖已销毁成员的槽。当前主窗口析构还显式断开一个工具模式连接，属于防御性处理。

## 六、CAD 几何、文件 IO 与 CAM（51–60）

### 51. CAD 几何为什么不能直接用 `==` 比较 double？

**参考回答：**

交点、投影和三角函数都会产生舍入误差，直接比较会让共线、相切和端点判断在缩放或大坐标下
不稳定。项目中的几何实现使用 epsilon、长度平方和有限性检查，并在布尔运算时指定 6 位精度。

epsilon 也不能到处写死同一个数。更稳妥的是根据模型尺度、操作语义和输入单位定义绝对/
相对容差；拓扑判断与显示容差要分开；对近退化输入返回明确失败或候选集合，而不是悄悄产生
NaN。

### 52. 多段线的 bulge 是什么，为什么要保留？

**参考回答：**

bulge 是每段圆弧圆心角四分之一的正切，符号表示方向。它允许 LWPOLYLINE 在两个顶点之间
表示真实圆弧，而不是离散折线。项目在绘制、镜像、反向、JOIN、TRIM、FILLET、DXF 42 组码
和原生格式中都保留 bulge；镜像时要改变符号，反向时还要同步段顺序和宽度数组。

保留解析弧能减少文件体积并提高后续编辑精度。只有偏移等复杂操作在必要时受控细分，并应
明确误差上限。

### 53. 修剪和延伸的核心难点是什么？

**参考回答：**

难点不是求任意交点，而是结合“目标实体、边界实体、用户拾取侧和实体有效区间”选择正确
解。直线、圆、圆弧和 bulge 段有不同参数域；延伸要选沿拾取端方向最近且位于有限边界上的
交点；修剪可能把一条实体拆成两条，并保持图层、线宽和弧方向。

我的工程原则是候选生成、候选过滤、拾取语义排序三步分开，预览与提交共用结果，并测试相切、
无交点、多个交点、端点重合和退化半径。

### 54. 圆角和倒角如何保证几何正确？

**参考回答：**

圆角本质是为两条支撑曲线寻找满足半径的相切圆，再按拾取侧确定切点并裁剪原实体；直线、
圆和圆弧组合需要枚举内外切候选并过滤有效区间。倒角则沿两条曲线按距离找点并连接，同时
检查相邻角处理是否重叠。

不能只看生成的连接段，还要验证切向连续性、半径、保留侧、属性继承和事务恢复。失败时应
保持原文档不变并给出可理解错误。

### 55. 为什么多边形布尔运算使用 Clipper2？

**参考回答：**

稳健的布尔运算涉及自交、孔洞、填充规则和数值鲁棒性，自研成本高且容易在边界输入失效。
项目把闭合 `SPoint2d` 路径转换成 Clipper2 `PathsD`，以 NonZero fill rule 和 6 位精度执行
并、交、差、异或和补集，再转换回自研类型。

公共接口不暴露第三方类型，异常被转成 `SResult`。代价是要理解精度缩放、方向/孔洞语义和
许可证，不能把调用库函数等同于自己解决了全部拓扑问题。

### 56. DXF 读写如何设计？

**参考回答：**

DXF 被解析为 group code/value 对，再按 SECTION、TABLE 和实体类型映射到文档。输出显式写
图层、颜色、线宽和实体字段；对不能无损表达的富文本、关联阵列或未知对象，通过
`SFileCompatibilityReport` 告知跳过或降级数量。

当前重点是常用二维实体，并不声称覆盖全部 AutoCAD 对象模型。现有导入会先清空目标文档，
图层创建也没有与实体事务形成完整原子边界；更安全的方案是先导入临时文档，全部成功后整体
交换。旧版代码页和非毫米单位也需要读取 `$DWGCODEPAGE` 与文档单位，而不能一律按 UTF-8、
毫米处理。解析器还应限制计数和内存预算、验证数值，并在失败时保持原文档不变。

### 57. 为什么 DWG 采用外部 LibreDWG 进程？

**参考回答：**

DWG 是复杂二进制格式，项目选择 LibreDWG 0.14 做转换，但不把 GPL 库 ABI 直接链接进自研
进程。导入路径是 DWG → 临时 R2000 DXF → 自研 DXF codec；导出是自研 DXF → 规范化 R2000
DXF → LibreDWG → 临时 DWG → `QSaveFile` 原子复制。

这种边界隔离了崩溃、依赖和内存分配器，也让 32 位主程序可在 64 位 Windows 上调用 64 位
工具；代价是额外进程、同步等待和格式降级，许可证义务仍需遵守。

**证据：** [`s_dwg_codec.cpp`](../sgraphIo/s_dwg_codec.cpp)。

### 58. 外部进程调用有哪些失败路径？

**参考回答：**

至少包括工具缺失、启动失败、超时、异常退出、非零退出码、输出文件未生成、stderr 警告、
临时目录失败、磁盘读写失败和最终原子提交失败。当前代码检查工具存在，设置受控 PATH 和
工作目录，启动最多等 10 秒、转换最多 120 秒，超时后 kill，并检查 exitStatus、exitCode 和
输出文件。

进一步生产化应增加异步取消、输入/输出大小限制、进程权限收缩、工具哈希校验、日志脱敏和
更精细错误分类，避免把任意 stderr 都当作相同故障。

### 59. 为什么需要兼容性报告？

**参考回答：**

文件转换不是二元的成功/失败。一个 DWG 可能成功导入 95 个实体、跳过 5 个代理对象；如果只
返回 true，用户会误以为无损。报告记录 imported/exported/skipped 和 warnings，GUI 可以在
操作成功后仍提示布局、代理对象、关联关系或富文本发生降级。

这是数据安全的一部分：软件宁可明确“不完整”，也不能静默丢数据。正式工作流还应允许用户
保存报告并保留源文件。

### 60. 刀路排序和仿真是如何实现的？

**参考回答：**

排序提供行扫描和最短优先两种模式。行扫描按垂直方向分行，再按左右方向稳定排序；最短模式
从起点反复选择距离最近的剩余实体，如果允许且实体可反向，还比较反向后的入口距离。排序
结果保留反向实体 ID。仿真把序列展开成 Rapid 和 Cutting motions，用定时器逐步推进，在
视口绘制已完成和当前轨迹。

最短模式是贪心启发式，不保证全局最优，复杂度约 O(N²)。更大规模可用空间索引、2-opt 或
分簇优化，但要同时约束加工方向、闭合轮廓入口和工艺规则，不能只优化欧氏距离。

**证据：** [`s_toolpath.cpp`](../sgraphGeometry/s_toolpath.cpp)、
[`s_toolpath_simulation_controller.cpp`](../sgraphGui/s_toolpath_simulation_controller.cpp)。

## 七、位图矢量化核心算法（61–75）

### 61. 为什么不用四邻域 flood fill，而要设计水平游程法？

**参考回答：**

两种方法的连通语义相同，都至少要读取一次全部像素；差别在中间表示。flood fill 为每个像素
维护标签和队列，并反复检查四个邻居。水平游程法先把一行连续同色像素压成一个区间，再只
比较相邻行的区间。在大色块、色带和规则图形中，游程数远小于像素数，能减少标签、队列、
分支和边界临时对象，也更符合顺序内存访问。

这不是宣称游程法在任何输入都更优。棋盘格中一个像素就可能是一条游程，中间规模会退化到
与像素数同阶；因此项目同时保留 flood fill 作为正确性和性能基线，用实测而不是只凭复杂度
判断。

### 62. 水平扫描线 A 到底是怎样得到的？

**参考回答：**

以某一行从左到右扫描，先计算像素的“有效颜色”：完全透明或被配置为背景的像素记为背景，
其他像素保留精确 ARGB。遇到前景像素时记录 `begin_x`，继续前进，直到颜色改变、进入背景
或到达行尾，把这段记录为半开区间 `[begin_x, end_x)`，同时保存 y 和颜色。接着从
`end_x` 继续扫描，直到整行结束。

所以 A 不是一条任意几何线，也不是仅有起终点的轮廓边，而是“一行内颜色完全相同且连续的
最大像素区间”。例如 x=2、3、4 为红色，A 就是红色 `[2,5)`，长度直接为 3。

### 63. 扫描线 A 与下一行扫描线 B 在什么条件下属于同一色块？

**参考回答：**

首先 A、B 都必须是前景且颜色精确相同；其次它们的 x 区间必须有正长度交集：

`max(A.begin_x, B.begin_x) < min(A.end_x, B.end_x)`。

这才是完整判据。不能只说“A 的起点或终点落在 B 内”，因为 B 可能完全包含 A，或者 A
完全包含 B；也不能把“两个端点都不在对方内部”直接当成不连通。只要两行存在至少一个相同
x 列，就有上下相邻的同色像素，四邻域下属于同一个连通分量。

**证据：** [`s_bitmap_run_vectorizer.cpp`](../sgraphIo/s_bitmap_run_vectorizer.cpp)。

### 64. 为什么使用半开区间，端点相等为什么不能连接？

**参考回答：**

半开区间 `[begin,end)` 的长度就是 `end-begin`，右端点同时是像素区域的右边界格线，避免
大量 `+1/-1`。两个区间只有在严格重叠时才有公共像素列。比如 `[2,4)` 表示 x=2、3，
`[4,7)` 表示 x=4、5、6；两者端点虽然相等，但没有共同 x，位于相邻行时只是角点接触，
不是四邻域连接。

如果改成闭区间，长度、重叠判据、右边界坐标和单元测试都必须同步修改，否则最容易出现的
错误就是把斜对角像素连成一个色块。

### 65. 如何保证四邻域语义，斜对角同色像素不会误连？

**参考回答：**

相邻行连接要求 x 区间有正长度交集。两个斜对角单像素分别对应 `[x,x+1)` 和
`[x+1,x+2)`，交集长度为零，因此不生成连接关系。项目还用 2×2 对角像素和棋盘格等定向
案例验证：同色像素只在角上接触时必须形成不同 component。

如果业务改成八邻域，不能简单把 `<` 改成 `<=` 就结束，因为角点处可能出现多条轮廓出边，
闭环选择、孔洞拓扑和规范化规则都要一起重新定义。

### 66. 颜色、背景和透明度的语义是什么？

**参考回答：**

算法不做 K-means、容差聚类或抗锯齿颜色合并，而是精确比较 `QRgb`，包括 alpha。完全透明
像素统一视为背景；启用忽略背景时，与选定背景色完全相同的像素也视为背景。没有显式选择
时可使用左上角颜色，这是界面便利策略，不是可靠的语义分割。

这样的好处是结果确定、可逐像素验证；代价是照片或抗锯齿图片会产生大量细碎颜色。那属于
预处理或颜色量化问题，应作为独立、可选步骤，不能混进本次连通算法的性能结论。

### 67. 游程提取的复杂度和缓存特征如何？

**参考回答：**

像素扫描是 O(P)，P 为像素数，这是无法绕过的下界。实现逐行顺序读取，分支主要发生在颜色
变化处；输出写入每行自己的连续容器，空间局部性较好。相邻行比较使用双指针推进，不对每对
游程做笛卡尔积，因此累计工作量主要与游程和实际重叠数量相关。

真正的收益来自常数和压缩后的中间规模，而不是把 O(P) 变成亚线性。性能解释中我会同时报告
P、游程数 R、连接/边界规模 E，避免只用大 O 隐藏碎片化输入的代价。

### 68. 为什么使用并查集，它在这里负责什么？

**参考回答：**

相邻行比较只能得到局部关系，例如 A 与 B 相连、B 又与下一行 C 相连；最终需要求这些关系
的传递闭包。每条前景游程先取得稳定 ID，每发现一对同色重叠游程就 union，最后同一根节点
代表一个四邻域色块。路径压缩和按秩合并使操作摊销接近常数。

并查集只解决“属于哪个 component”，不负责轮廓次序，也不赋予根 ID 几何含义。最终输出
仍需按稳定规则重新编号、压缩边界并规范化，否则线程调度或 union 顺序可能污染结果顺序。

### 69. 一对多、多对一、分叉和汇合怎样处理？

**参考回答：**

相邻两行的游程采用双指针扫描，但不会在找到第一个重叠后就停止。只要同色区间有正交集，
就记录一条 join。因此一条上行游程可以与多条下行游程连接，多条上行游程也可以汇合到一条
下行游程。所有 join 送入并查集后，它们自然成为同一连通分量。

这正是“只比较 A、B 两个端点”容易出错的地方。正确实现必须覆盖包含、被包含、部分交叉、
一对多和多对一，并用分叉/汇合构造图做定向测试。

### 70. 色块边界线段是怎样生成的？

**参考回答：**

边界定义在像素格线而不是像素中心上。每条前景游程贡献左右竖边；第一行贡献上边，最后一行
贡献下边。相邻两行比较时，只要同一 x 区间的有效颜色不同，就分别为上下两个前景区域生成
方向相反的水平边。这样每一条“前景—背景”或“异色—异色”界面都归属到相应色块。

不同颜色区域共享同一几何边时会各自拥有一条方向相反的有向边，这是两个色块的合法边界，
不是需要去重的重复线段。

### 71. 为什么还要压缩边界线段，怎样防止错误合并？

**参考回答：**

扫描阶段产生的边界可能被切成很多短段。压缩时先规范成“色块、颜色、方向、固定坐标、
low、high”，排序后只合并同色块、同颜色、同方向、同一直线且首尾相接的区间。方向必须在
键中，否则共享边界上的反向线段会被误合并。

实现还拒绝零长度边和同一规范线上的重叠/重复边，而不是静默吞掉。压缩既减少后续哈希和
SVG 顶点数量，也是对边界生成不变量的一次主动校验。

### 72. 无序线段如何拼接成闭合轮廓？

**参考回答：**

线段先按 component 分组，再建立“起点坐标 → 未消费出边”的索引。从任一未消费边开始，
沿当前终点查找下一条出边，逐条标记已消费，直到回到起点。一组线段可能拼出多个环，例如
一个外环和若干孔洞。全部完成后必须保证每条边恰好消费一次。

若找不到下一边、边被重复消费、超过保护步数仍未闭合，或简化后少于三个顶点，算法返回
失败而不是输出损坏 SVG。这使拓扑错误能在测试阶段被定位。

**证据：** [`s_bitmap_contour_stitcher.cpp`](../sgraphIo/s_bitmap_contour_stitcher.cpp)。

### 73. 一个顶点有多条候选边时如何选择？

**参考回答：**

方向编码为右、下、左、上；相对于上一条边，按右转、直行、左转、回头的稳定优先级选择。
在屏幕坐标 y 向下的体系中，这能持续沿色块边界前进。若同一优先级仍出现多个候选，实现会
把它视为无法消解的分支并报错，而不是依赖容器迭代顺序随便选一条。

这个规则建立在四邻域、整数网格和 component 已正确分组的前提上，不是任意平面线网的通用
拓扑修复算法。

### 74. 如何让单线程和多线程输出具有确定性？

**参考回答：**

并行阶段只写固定索引的行结果或相邻行连接结果；等待全部任务结束后，主线程再按 y、x 顺序
分配游程 ID，并按稳定数组顺序执行 union。线段随后排序，共线点被删除，每个闭环旋转到
`(y,x)` 最小顶点作为固定起点，最终轮廓再按稳定键排序。

因此线程完成先后不会进入序列化结果。基准不仅比较语义哈希，还要求单线程和多线程生成的
SVG 字节完全一致；这对复现问题、缓存和版本回归都比“看起来一样”更有价值。

### 75. 孔洞如何表示，轮廓方向是否已经完全验证？

**参考回答：**

同一 component 可以有一个外环和多个内环；SVG 把同色环写入 path 的多个闭合子路径，并用
`fill-rule="evenodd"`，所以孔洞显示不依赖绕向。边生成规则通常会自然产生相反方向，项目
也验证了带孔图能得到一个 component、两个 contour、可解析且回栅格一致。

需要诚实说明：当前基准没有单独计算有符号面积来断言“所有外环和孔洞方向都符合某一约定”。
现有证据验证的是闭合、偶奇填充和像素结果。如果要支持 nonzero fill 或下游 CAM 对方向有
严格要求，应新增显式方向规范化和方向断言。

## 八、并发、性能与基准方法（76–85）

### 76. 多线程方案具体并行了哪些阶段？

**参考回答：**

第一阶段按连续行区间并行提取水平游程；第二阶段按相邻行边界区间并行计算 join 和水平边界
段。游程 ID 分配、并查集合并、component 编号、线段压缩、闭环和 SVG 序列化仍在主线程
串行执行。

选择这两个阶段是因为它们输出位置天然可分割，能无锁并行并保持确定性。它不是“整条链路
全并行”，所以加速最终受串行阶段和任务调度限制；若 profiling 显示拼接成为瓶颈，可以再按
component 并行，但要先解决稳定排序、内存峰值和错误聚合。

### 77. 自动线程数和任务粒度怎样确定？

**参考回答：**

显式传入正数时使用指定线程数。自动模式下，小于 1,048,576 像素的图直接单线程，达到阈值
后取 `QThread::idealThreadCount()`；任务数最多约为 worker 数的四倍，再把行或行间边界切成
连续区间。适度超分能平衡不同区域的游程密度，又避免“一行一个 future”的调度开销。

阈值是基于当前实现和测试环境的工程参数，不是理论常数。更成熟的策略可以结合宽高、颜色
变化率、历史采样和线程池复用动态决策，并通过不同 CPU 的基准重新标定。

### 78. 并行实现如何避免数据竞争和悬空引用？

**参考回答：**

提取阶段每个任务只写 `rows[row]` 的独立槽位；连接阶段每个任务只写
`connections[index]` 的独立槽位，源图和已完成游程只读。热循环不共享 push_back 容器，
所以不需要锁。函数在使用结果和销毁局部对象前显式等待全部 `QFuture` 完成，闭包捕获的引用
在任务生命周期内有效。

“不同线程写 vector 的不同元素”成立的前提是外层 vector 已经定长，任务期间不会扩容或
改变结构。这个不变量应通过代码结构和 ThreadSanitizer 类工具继续守护，而不能只靠注释。

### 79. 怎样证明并发结果可重复，而不是偶然相同？

**参考回答：**

确定性来自设计和测试两层。设计上，并行任务只生产带固定位置的中间结果，所有会决定 ID、
union 顺序和输出排序的步骤都在 join 后稳定执行；轮廓起点与列表顺序也被规范化。测试上，
同一输入分别运行串行和自动并行，比较 component 数、带颜色轮廓哈希，并要求 SVG 字节完全
一致。

重复 5000 次不等于形式证明，但能覆盖广泛拓扑；再结合无共享写入的结构、定向极端案例和
竞态检测，证据链比只比较渲染截图更完整。

### 80. 整体时间复杂度和最坏输入是什么？

**参考回答：**

设像素数 P、前景游程数 R、连接和边界规模 E。扫描为 O(P)，相邻行双指针比较与游程/重叠
规模相关，并查集约 O(R·α(R))，线段规范化排序 O(E log E)，拼接大体 O(E)，另有轮廓排序。
因此不能简单说全程 O(P)。

规则大色块中 R、E 远小于 P；单像素棋盘格中 R 和 E 都可与 P 同阶，且输出本身包含海量独立
轮廓，排序和序列化会主导。这是输出敏感问题，不可能靠线程把必要输出成本消除。

### 81. 游程法一定更省内存吗？内存指标怎样理解？

**参考回答：**

flood fill 基线固定维护整图整型标签，并可能有较大 BFS 队列；游程法保存每行游程、连接、
并查集和边界。大而平滑的图上 R≪P，游程法通常更省；棋盘格中 R≈P，还会产生大量边界，
优势可能消失。

代码中的 `estimated_working_bytes` 只是主要数组的粗估，不包含所有 vector capacity、嵌套
容器、哈希表、轮廓、SVG、QImage 和线程运行时。报告中的进程峰值工作集更接近总体上界，但
三种算法在同一进程轮换运行，也不能直接拆成单算法精确峰值；要做严格归因，应隔离子进程或
采样分阶段分配。

### 82. 基准怎样减少文件 IO、缓存和执行顺序偏差？

**参考回答：**

测试图片先生成并保存，正式计时前只解码一次；三种算法都接收同一个 `QImage`，PNG 读取、
正确性复核和报告生成不计入算法时间。三种方案的执行顺序按案例轮换，避免某个方案永远先跑
或总享受热缓存；每个方案默认运行三次并取中位数，降低偶发调度抖动。

计时口径仍包含算法内部的像素格式转换、扫描、连接、闭环和 SVG 序列化，因为这些是调用者
实际承担的端到端转换成本。报告比较的是本项目三种实现，而不是某个抽象算法的理论极限。

### 83. 基准是否真的做了“预热后执行三次”？

**参考回答：**

按当前源码，答案是否定的：每个方案执行三次并取中位数，但没有单独的、计时外预热轮次，
第一次也进入三个样本。因此我不会把计划文档中的“预热”当成已实现事实。中位数和顺序轮换
能减弱部分冷启动影响，却不能完全替代显式预热。

改进方式是每种算法先执行一次不计时预热，再计时至少三次；同时记录 CPU、编译器、频率策略
和系统负载。对极短小图还应批量循环后除以次数，降低计时器分辨率和调度噪声。

### 84. 正确性验证链具体包括什么？

**参考回答：**

三种方案先比较 component 数；轮廓按颜色和点序列规范化后计算 SHA-256 并排序比较；串行与
并行 SVG 还做字节级比较。三份 SVG 都交给项目现有解析器重新读取；三份直接生成的轮廓分别
按像素中心回栅格，与输入逐像素比较。拼接器内部还检查零长度、重叠边、重复消费、开放端点、
无法消解的分支和退化闭环。

失败不会中止整批测试，而是保存输入图、三份 SVG 和像素差异图。边界也要说清：当前没有把
“重新解析后的 SVG”再次栅格比较，也没有单列每个 component 的面积表；像素面积和颜色主要
由直接轮廓回栅格及带颜色哈希覆盖。

### 85. 实测到底说明了什么，能否断言“多线程一定更快”？

**参考回答：**

均衡度较高的 1000 文件测试中，正确性 1000/1000；flood fill、游程单线程、自动多线程累计
分别为 19,618.17、7,015.54、4,879.50 ms，所以游程表示本身相对基线约 2.80×，并行在此
基础上约 1.44×，总计 4.02×。5000 文件测试为 5000/5000，通过，三者累计
1,216,018.72、279,075.69、102,223.19 ms，即 11.90× 和 2.73×。

但 5000 组中有 4010 张 4096×4096，更接近大图耐久/压力分布，不能当作均衡总体；小图和
棋盘格也可能不加速甚至变慢。准确结论是：在本机、本实现、精确颜色四邻域和相应输入分布
下，方案可行且累计更快；不能承诺每个文件、每台机器都更快。

**证据：** [测试结果](TEST_RESULTS.md)、
[正式报告](../sgraphVectorBenchmark/results/5000-case-20260727/bitmap_vector_benchmark_report.html)。

## 九、测试、构建、发布与工程质量（86–95）

### 86. 自动测试是怎样组织的？

**参考回答：**

日常 CTest 共 32 项：31 项覆盖文档事务、持久化、恢复、审计、DXF/DWG、SVG、视口交互、
捕捉、曲线、阵列、填充、快捷键、工作区、刀路等，另有 20 图的位图矢量化冒烟测试。完整
1000/5000 文件基准不进入默认 CTest，以免拖慢日常反馈，而由独立 Release 工具按需执行。

测试目标只链接必要模块，便于定位层级问题。下一步会按“纯几何单元测试、文档集成测试、
GUI 交互测试、长时基准”进一步标记和并行调度，并为随机测试保存 seed 和最小失败样例。

### 87. Qt GUI 测试在无人值守环境中如何运行？

**参考回答：**

CI 和普通 CTest 可设置 `QT_QPA_PLATFORM=offscreen`，让依赖 QApplication 的测试不需要真实
桌面；交互通过 QTest 发送鼠标键盘事件，再验证文档、命令状态和视口变换，而不是只检查函数
返回值。这样适合自动回归，但 offscreen 不能证明所有显卡、DPI、字体和窗口管理行为正确。

因此发布前仍需要真实 Windows 机器上的人工视觉验收，尤其是 Ribbon、Dock、OpenGL 上下文、
高 DPI、多屏和输入法；自动测试负责可重复逻辑，人工测试负责视觉和平台组合，两者不能互相
冒充。

### 88. 测试图片如何生成并保证可复现？

**参考回答：**

默认总种子为 `20260727`，案例根据编号派生独立种子，文件名和 `manifest.json` 记录编号、
类别、尺寸、颜色数和生成参数。覆盖纯色/色带、凹形/孔洞、分叉汇合、细线通道、斜对角/
棋盘格、随机矩形及真实样例变体。失败时可用同一 seed 和案例编号复现。

1000 案例的尺寸配额相对均衡；当前 5000 生成逻辑在 991 号后持续生成 4096×4096，导致
4010 张超大图，所以它应标为压力分布。还可改进为把配额参数写入 manifest、校验复用 PNG
内容哈希，并加入 delta debugging 自动缩小失败图。

### 89. 为什么失败后继续跑，报告和附件怎样帮助定位？

**参考回答：**

批量基准的目标不只是给一个绿灯，还要一次发现错误分布。因此单例异常或不一致被记录后继续
下一文件，最终统一返回非零状态。报告汇总通过率、累计耗时、分位数、类别/尺寸分组、最慢和
退化案例，并保留全部逐文件明细。

失败目录保存原输入、flood/串行/并行三份 SVG 和差异图。开发者能先看差异集中在角点、孔洞
还是颜色，再用 manifest 中 seed 和尺寸复现；这比只有 assertion 行号更接近可诊断测试。

### 90. CMake 工程有哪些值得讲的设计？

**参考回答：**

根工程统一 C++17、关闭编译器扩展，启用 AUTOMOC/AUTORCC/AUTOUIC，并用 target 表达
Core→Geometry→Document→Commands/IO→Render→GUI→App 的依赖。MSVC 使用 `/W4`、
`/permissive-`、`/Zc:__cplusplus` 和 `/utf-8`。第三方示例和测试通过 cache 选项关闭，
项目测试由统一开关接入 CTest。

MSVC+Ninja 时设置 `VSLANG=1033`，是因为 Ninja 需要稳定解析 `/showIncludes` 依赖输出，
避免本地化文本导致头文件变化却未触发重编译。当前不足是部分依赖声明过度 `PUBLIC`，还缺
安装/导出规则和正式 Presets，需要继续收紧接口面。

### 91. 构建脚本怎样自动找到并验证 Qt？

**参考回答：**

候选顺序是显式 `--qt-dir`、架构专用环境变量、`QTDIR`、项目 `.toolchain/Qt`、常见安装
目录、用户目录和 PATH 中的 qmake，并展开 `msvc2017`/`msvc2017_64` 套件。找到目录后不只
检查存在性，还要求 qmake、`Qt5Config.cmake`、配置对应 Core DLL 和 `windeployqt` 齐全，
通过 qmake 验证版本精确为 5.12.10，再解析 Core DLL 的 PE machine 确认 x86/x64。

这能把“选错 Qt”提前变成清晰的配置错误，而不是链接阶段才报一串符号问题。手工绕过 Python
直接调用 CMake 时，严格校验能力没有完全等价，这也是推荐统一入口的原因。

**证据：** [`s_build_common.py`](../sgraphBuildTools/s_build_common.py)、
[编译说明](BUILDING.md)。

### 92. 32 位支持是真实的吗？有什么限制？

**参考回答：**

32 位入口会调用 VS 的 `vcvarsall x86`、选择 x86 Qt kit、输出到 `build/32/<Config>`，构建
结束再解析 EXE 和运行 DLL 的 PE 头，混入 x64 就失败；64 位走对应 amd64 链路。项目记录的
四种本地配置各通过 32/32 CTest 和启动验证，因此不是只改目录名。

限制是随包 LibreDWG 为独立 x64 程序。x86 主程序能在 64 位 Windows 启动它，但纯 32 位
Windows 不能使用完整 DWG 能力。准确承诺应是“提供 x86 应用构建，DWG 转换要求 64 位
Windows”，或者未来补齐 x86 转换工具。

### 93. Qt 运行库和发布包如何自动部署、校验？

**参考回答：**

应用构建后调用同一 Qt kit 的 `windeployqt`，复制 Core/GUI/Widgets 依赖、platforms 和图像
插件等，同时复制 QtADS DLL、翻译和 LibreDWG 工具。脚本随后检查关键运行文件并生成
`runtime_manifest.json`，记录相对路径、大小、SHA-256、PE 架构和来源；打包 ZIP 后再生成
整包 SHA-256。

哈希能帮助发现损坏和混装，但不能证明发布者身份，manifest 本身也可能被一起篡改。正式
GitHub Release 还应增加 Authenticode 签名、受保护的发布工作流、SBOM 和可验证的版本标签。

### 94. GitHub Actions 当前覆盖什么，还缺什么？

**参考回答：**

当前工作流在 Windows 上配置 Qt 和 MSVC/Ninja，构建并测试 32 位 Release 与 64 位 Release，
能防止主要发布架构在干净环境中失效。Debug 虽在本机四套验证中通过，但当前 CI 矩阵没有
覆盖，不能说“四种配置都由 GitHub 持续验证”。

下一步会把 Debug 作为轻量编译/核心测试矩阵，Release 做完整测试；再加入格式检查、静态
分析、依赖许可证/SBOM、发布包冒烟和可选 sanitizer。长时 5000 图基准适合定期或手动工作流，
不应让每个提交都等待数小时。

### 95. 第三方依赖、许可证和仓库发布状态怎样说明？

**参考回答：**

SARibbon、QtADS、Clipper2 和 LibreDWG 统一放在 `sgraphThirdParty`，构建可离线复用确定版本；
Qt SDK 因体积和许可边界不进 Git，要求用户安装 5.12.10，再由脚本自动发现。各组件的来源、

项目自身采用 source-available 许可，不能把它表述为 OSI 意义的开源。并且截至证据基线，
Git 仓库尚未形成首个提交和远程地址，所以准确状态是“已按 GitHub 发布标准整理，待首次

## 十、缺陷复盘、演进与综合追问（96–100）

### 96. 讲一个你定位并修复的真实 Bug

**参考回答：**

对象捕捉曾出现“启用端点/圆心过滤后，其他捕捉类型也消失”的问题。根因不是几何计算，而是
过滤条件把一个布尔开关写成了所有候选的总门禁：当候选不是端点或圆心时也被拒绝。修复时
我先构造包含端点、中点、交点、圆心的最小文档，分别切换每个开关，确认失效矩阵，再把条件
改为“只有候选属于对应类型时，才查询那个类型的开关”。

回归测试覆盖单开关、组合开关和默认配置，并验证返回的捕捉类型与坐标。这个案例说明复杂
交互 Bug 要先分离“候选生成”和“候选策略过滤”，不能只在界面里试到看似正常。

### 97. 再讲一个由字符串处理引起的 Bug

**参考回答：**

SVG 导入曾因正则表达式转义和匹配范围处理不当，导致某些合法 path/属性无法读取。我的处理
不是只改一个反斜杠，而是先保留触发文件，确认问题发生在 XML 属性获取、数字 token 化还是
path 命令解析，再用最小字符串固定预期；修复后加入包含科学计数、负数相邻、空白/逗号组合、
闭合命令和多子路径的回归。

复盘结论是：正则适合局部 token，不适合替代完整 XML 解析或状态机。外部格式输入还要限制
长度、检查完整消费并给出上下文错误，避免“部分匹配成功”静默接受损坏数据。

### 98. 项目已改名，为什么代码里仍有 smartCad？

**参考回答：**

我会先区分兼容标识和普通债务。原生文件 magic `SMCAD001`、manifest 标识以及可能影响
QSettings 路径的 organization name，直接改掉会破坏旧文档或用户配置，应该通过双读单写、
版本迁移和弃用周期处理。`SMARTCAD_BUILD_TESTS`、内部宏和部分 target 名不承担外部数据
兼容，则属于可清理债务，可新增 `SGRAPH_*` 名称并暂时保留旧别名。

所以现状不是“改名漏改了几个字符串”这么简单，也不能声称零残留。正确做法是先建立标识
清单，给每项标注文件兼容、设置兼容、API/构建兼容或纯内部，再制定迁移测试。

### 99. 如果有一个月继续重构，你最先做什么？

**参考回答：**

第一周先处理可靠性：把命令状态从较大的 viewport 中抽成显式状态机，完善事务异常安全和
原生格式分块校验。第二周做性能基础设施：持久线程池、阶段级 profiling、解析后 SVG
回栅格、显式预热，并恢复均衡的 5000 案例尺寸配额。第三周做可扩展性：文档实体/空间索引、
历史记录增量存储、IO codec 注册和长任务取消。第四周做交付：补 Debug CI、静态分析、SBOM、
签名流程和文档事实自动校验。

排序依据是风险和证据，不是重写冲动。当前 `s_implementation_status.md` 仍写 1000 案例和
旧文件版本，而源码已是版本 24、报告已到 5000；这种文档漂移也应由 CI 中的元数据生成或
一致性检查解决。

### 100. 为什么这个项目能证明你适合 C++/Qt/CAD 岗位？
