## 历史性能与内存记录

批量删除原先对每个删除项遍历并压缩一次实体数组，且闭包按值复制整个实体。
现在先建立 ID 集合，再做一次稳定压缩；单 ID 保留不建哈希表的快速路径。
平均复杂度由 O(N×K) 降至 O(N+K)，临时 ID 存储为 O(K)，不增加常驻文档索引。

在本机 MSVC 14.44、x64 Release `/O2` 下，固定每个实体 128 个 double，每 5 个删除 1 个，
连续 3 次测量的中位数如下。构造输入不计时，两个算法输出逐项比较一致。

| 实体数 / 删除数 | 原删除阶段 | 新删除阶段 | 原记录复制次数 → 新 |
| --- | ---: | ---: | ---: |
| 1,000 / 200 | 0.1758 ms | 0.0294 ms | 200 → 0 |
| 10,000 / 2,000 | 16.69 ms | 0.3637 ms | 2,000 → 0 |
| 30,000 / 6,000 | 152.791 ms | 1.4366 ms | 6,000 → 0 |

最后一组累计几何载荷复制由 6,144,000 字节降为 0，实体移动赋值由 90,009,000 次降至
24,000 次。这是集合删除内核的合成基准，不包含事务准备、历史保存、渲染和 Qt 通知，
也不是应用整体加速或峰值内存测量。哈希集合仍会分配 ID 存储。

正式 CMake 基准目标的最终单次复验同样逐项相等，3 万实体结果为 144.856 ms →
1.2951 ms；原始输出位于本地 `build/vp_id_collection_benchmark.csv`，不进入 Git。

可复现基准源：`sgraphTests/vp_id_collection_benchmark.cpp`；正式构建目标
`vectorPathIdCollectionBenchmark` 默认不构建、不计入测试时间门槛；当前复现命令为：

```powershell
python sgraphBuildTools/vp_build.py --core --benchmarks
build/core/64/Release/sgraphTests/vectorPathIdCollectionBenchmark.exe
```

普通事务原来无条件在历史项保存一份全量 ID 数组，现在不再保存；每个历史项节省的有效
载荷为实体数 × 8 字节（例如 100 万实体约 8 MB，不含容器与分配器开销）。
11 个实体创建入口改为移动进入事务暂存区，避免多段线、填充边界等几何的一次额外复制；
文档与历史之间为撤销保留的必要副本没有删除。

## 后续迁移顺序

1. 迁移领域文本、颜色、图层与样式类型；保留 Qt 的 Unicode 比较/修剪和颜色语义，先补边界测试。
2. 提取文档状态、历史和同步类型化通知；分离文件路径/保存状态、原生编解码及恢复调度。
3. 抽离完整工具生命周期、选择、夹点、预览和命令编排；保持入口、别名、事务粒度和操作顺序。
4. 完成全核心无 Qt 构建与桌面适配收敛，再基于实际使用剖析选择后续性能优化。

已识别但本阶段未改变的既有行为：创建实体时可能在提交前创建颜色图层，取消并不总能撤回
该图层；`setEntityOrder` 后再向同一事务新增实体可能产生不完整重排集合。这些需在后续
事务设计中用单独回归用例界定，不能将它们误报为本阶段已修复。
